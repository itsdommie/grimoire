# Grimoire: a local-first MTG deck lab

**End goal: an easy-to-install, one-stop desktop application for all things Magic: The Gathering, for Windows and Linux** (no macOS). Double-click installer, no Node/Python/Docker for the user, works offline after the first card-data download, no account, no paywall. It treats the whole card pool as a database you can query and simulate against, and uses a GPU when present but never requires one. **Commander first.**

Until the packaged app exists we develop it as a web app (React + local server); the desktop shell wraps the same code.

## Features (build order)

1. **Local card database.** Ingest Scryfall bulk data (Oracle Cards, ~160 MB) into SQLite. Support a Scryfall-style search syntax (`t:creature c:rg cmc<=3 o:"draw a card"`). Millisecond queries, works offline.
2. **Commander deck builder.** Legality, colour identity and singleton checks. Import/export Moxfield, Archidekt and plain-text lists. Standard and Modern later.
3. **Deck analysis.** Mana curve and colour pip distribution. Land-count and colour-source recommendations (Karsten's published mana math). Automatic role tagging (ramp, draw, removal, wipes, win conditions) with a "you're short on X" report.
4. **Goldfish simulator.** 10,000+ Monte Carlo games in a Web Worker: opening hands, mulligans, on-curve rate, colour-screw rate, typical turn the game plan comes online.
5. **Semantic card search.** Local embeddings of rules text on the GPU (default `bge-small` via `sentence-transformers`, Python venv). No API key needed.
6. **Collection tracker.** Import ManaBox/Moxfield CSVs, Scryfall prices, "what can I build from what I own?", "cheapest way to finish this deck".
7. **Claude advisor (OPTIONAL).** Chat panel whose tool calls hit the local database, so every suggestion is a real, legal card. Requires `ANTHROPIC_API_KEY`. Without it the panel reads "not configured" and the rest of the app is unaffected. The key is never written to the repo.

## Tech

TypeScript throughout. React + Vite frontend, small Fastify server, SQLite (`better-sqlite3`), Vitest. npm (not pnpm). Rules logic and the simulator get real tests, including checks against hypergeometric probabilities. Playwright end-to-end tests for the UI.

**Desktop packaging (decided): Electron + electron-builder.** It runs the existing Fastify/better-sqlite3 code unchanged in the main process (or a utility process), and produces an NSIS `.exe` installer for Windows and AppImage + `.deb` for Linux. Tauri is the lighter alternative but would mean shipping the Node server as a sidecar or rewriting the backend in Rust, so it's not worth it here.

Consequences for the design:
- **Data location:** the DB and downloaded Scryfall data live in the per-user app-data directory (`app.getPath('userData')`), not the repo. First run downloads the bulk data with a progress screen; a "check for updates" action re-ingests.
- **Semantic search (Phase 3):** no Python venv in the shipped app. Run `bge-small` as ONNX through `onnxruntime-node` (CPU by default, CUDA/DirectML optional), with embeddings precomputed or built on first run.
- **Claude advisor key:** stored via the OS keychain (Electron `safeStorage`), never on disk in plain text or in the repo.
- **Simulator:** Web Worker in the renderer, so it needs nothing native.
- **No native modules:** SQLite is Node's built-in `node:sqlite` (Electron 44 ships Node 24 with it, FTS5 included), so there is nothing to rebuild per platform. Windows installers are built on Windows (CI); Linux on Linux.
- **Docker / self-hosting** is demoted to an optional mode, not the main delivery path.

Each phase ends with something usable.

## Ground rules

- **Scryfall:** use bulk data rather than hammering the API, send a proper `User-Agent` and `Accept` header, respect rate limits, hotlink card images (never re-host, crop or alter them), attribute Scryfall.
- **Wizards:** non-commercial, per the Fan Content Policy.
- **GitHub:** the repo is public (MIT) and releases are published from it; never commit secrets, tokens or personal data.
- **Secrets:** never commit API keys or tokens.
- **Environment:** Node 26, SQLite 3.53, Git, `gh`. Dev machine is Linux, so Windows installers need CI or a cross-build; testing them locally isn't possible here. Docker needs sudo/daemon fixes if the optional self-hosted mode is built.
- **Distribution:** Windows and Linux only. Never require end users to install Node, Python or Docker. Don't push to GitHub (needed for CI builds) until asked.

- **Android and printings (2026-10-03):** the on-device card database is copied into the app's storage on first launch and never replaced (it also holds the user's decks and collection), so card data updates are a separate mechanism (next bullet). Printings sidestep that: `build.mjs` strips them from the bundled database and ships them as `card-printings.json` (plain JSON, ~6 MB in the APK) plus `bundled.json` with its version; `api.worker.ts` loads it at startup when the install has none or an older version (ISO dates compare as text), so fresh installs and in-place app updates both get current printings, offline, with a 'Loading card printings…' splash message. Fresh install to the card grid: ~7 s on the emulator (2 s afterwards). LESSON: Android's asset packager strips a `.gz` extension (the file is in the APK without it), so the first version asked for a name that doesn't exist and the worker died with 'Can't reach Grimoire's local service' only on the device, not in any browser test; never ship `.gz` assets. Also: a clean Gradle build is ~79 MB, an incremental one leaves dead space (~117 MB), so build the distributed APK clean.
- **Android card data updates (2026-10-03, working, not released):** `card-data.yml` (weekly, `cli carddata --export`) publishes `card-data.db.gz` + `card-data.json` to the `card-data` prerelease: a database of ONLY the card tables (`CARD_DATA_TABLES` + the two FTS tables + the `CARD_DATA_META` keys, no indexes, no embeddings, no user tables; the app keeps its own indexes) plus a manifest {version = Scryfall bulk `updated_at`, dataVersion, schema, cards, size}. The app (`cardUpdates.ts` in the worker) checks the manifest weekly 10 s after start or on 'Check for card updates', refuses data from a newer schema/dataVersion ('update the app'), streams the file gunzipped (DecompressionStream) into a second OPFS file `/card-data-next.db`, sets `meta.card_data_pending`, and tells the page to reload; at the next start `applyPendingCardData` runs BEFORE the router exists: `applyCardData` (neutral, in `carddata.ts`, tested in Node with node:sqlite files) ATTACHes the file, checks its schema and a 1000-card floor, then in ONE transaction replaces each card table (columns matched by name), rebuilds the FTS tables and copies the data meta keys; a failure rolls everything back, is recorded as `card_data_error` (shown as a warning) and never stops the app. User tables (decks, deck_cards, collection, collection_prints, embeddings) are not listed, so are never touched; deck/collection rows name cards by oracle id and printings by Scryfall id, so they survive even when a card disappears. Metered connection (`navigator.connection` cellular/saveData, forced by `localStorage grimoire.metered`): the weekly look only sets `status.available` (size shown in the footer with a Download button); a manual request always downloads. WHY NATIVE DOWNLOAD: GitHub release downloads 302 to a CDN and neither response has CORS headers, so a web page (or worker) cannot fetch them (verified with curl); on the phone the bridge downloads through Capacitor's Filesystem plugin (native HTTP, streams to the cache dir), and the worker reads the file back from the app's local file URL (`Capacitor.convertFileSrc`), then deletes it; the worker asks the page via `native` messages (protocol.ts). In a plain browser (tests) the worker just fetches. `network_security_config.xml` allows cleartext only to 10.0.2.2 and localhost so the emulator test can reach the machine it runs on. Tests: Node unit tests (swap, atomicity, user data intact, version/damage refusals, columns by name), two Chromium specs (weekly check applies it; metered says available then downloads), and on the emulator the real native path end to end (`android-update.spec.ts`: update built from the real database, served from the host, downloaded natively, applied, deck and collection intact) plus a kill-mid-first-launch recovery spec. Lessons: killing the app mid-copy is harmless (the SAH pool only shows a database once its import completed). A page RELOAD races the old worker letting go of its OPFS files: measured on a fast idle desktop, 6 of 12 quick reloads failed to start ('Access Handles cannot be created…', shown as 'Can't reach Grimoire's local service'), and it failed three tests on the slower CI runner (the ones that reload). Fix: `installPool` retries every 250 ms for ~7 s with `forceReinitIfPreviouslyFailed: true` (the pool caches a failed init, so a plain retry does nothing); after that 0 of 12 failed. The card-update apply step depends on this, because it reloads the page. An earlier retry without that option looked useless, and I wrongly removed it: always measure (reload in a loop) rather than reason.
